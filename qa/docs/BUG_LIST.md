# Список ошибок по итогам проверки (28.10.2026)

Приоритеты: **P1** — ломает пользовательский путь или скрывает причину отказа; **P2** — мешает проверке или качеству, но есть обход; **P3** — косметика и тестовые данные.

Прогон: Backend в режиме `GENERATOR_MODE=llm_service`, LLM-сервис в `LLM_SERVICE_FIXTURE_MODE=true`. Каталог — 14 событий. Проверялись HTTP-путь, `quality_report`, ошибки и `partial`.

## P1

### BUG-01. Фронтенд не обрабатывает `partial` и уходит в таймаут

- **Где:** `frontend/src/api.ts`, `createProject` (строки 20–26).
- **Шаги:** запросить 3 варианта для `knowledge_day`, дождаться статуса `partial`.
- **Факт:** Backend отдаёт `job.status=partial`, `project.status=partial`, `completed_variants=1`, готовый вариант доступен в проекте. Фронтенд ждёт только `completed`, крутит цикл 90 × 1,2 с и через ~108 секунд показывает «Превышено время ожидания генерации». Причина `partial` в этом прогоне — fixture-режим (BUG-04); для фронтенда это не важно, поведение будет тем же при отказе реальной модели.
- **Ожидаемо:** показать готовые варианты и предупреждение, что часть вариантов не готова (ТЗ 16.6, критерии приёмки, раздел 2).
- **Влияние:** пользователь не получает готовый сценарий и видит ложную ошибку.

### BUG-02. `failed` и `partial` не объясняют причину

- **Где:** `services/school_events_llm/app/http_api.py` (`finish_generation`), `app/generation/pipeline.py` (`VariantOutcome`), контракт 02.
- **Шаги:** отправить запрос, который не проходит проверку плана; сравнить HTTP-ответ и CLI.
- **Факт:** через HTTP `job.errors=[]`, в `project.variants` нет ни одного варианта и нет причины. CLI на том же запросе показывает: `failed / План не прошёл проверку / critical:PLAN-PUPILS:roles, critical:PARENTS-DISABLED:roles`.
- **Ожидаемо:** причина отказа и список issue доступны в `job` или в проекте для каждого варианта (ТЗ 16.2, контракт 02).
- **Влияние:** фронтенд не может показать, что именно не так; поддержка и QA диагностируют только по логам и CLI.

### BUG-03. Внутренняя арифметика блока не проверяется: реальный сценарий теряет время

- **Где:** сценарий Андрея `qa/docs/scenario (2).md`, «Весенний трудовой марафон»; автоматические проверки тайминга (`check_grid`, `TIMING-*`).
- **Факт:** блок 15–30 мин (15 мин) содержит 10 минут подготовки команд **и** выступления команд; блок 45–55 мин (10 мин) требует представить 5 команд по «максимум 3 минуты», то есть до 15 минут; блок 30–45 мин начинается словами «После завершения выступлений команд», хотя в нём же запланирована работа с листом на 10 минут. Сумма блоков при этом ровно 60 минут, поэтому автоматика пропускает сценарий без замечаний по таймингу.
- **Ожидаемо:** либо автоматическая проверка бюджета действий внутри блока, либо обязательное экспертное замечание уровня `high`.
- **Влияние:** педагог физически не успевает провести сценарий; это дефект качества, а не форматная ошибка.

## P2

### BUG-04. Fixture-режим по HTTP выбирает эталон не по событию

- **Где:** `services/school_events_llm/app/llm/fixture.py`, `_golden()`.
- **Факт:** `mothers_day` (30 мин) и `labour_day` (60 мин) через HTTP завершаются `failed`, хотя CLI с соответствующим эталоном (`--fixture examples/golden/ex2_mothers_day.json` / `ex3_labour_day.json`) завершает их как `completed`. HTTP-клиент берёт эталон по порядку (`goldens[0]` для `v1`), а не по `event_id`.
- **Ожидаемо:** эталон выбирается по событию запроса; иначе fixture-режим пригоден только для `knowledge_day`.
- **Влияние:** нельзя прогнать E2E и демо на других событиях без реальной модели.

### BUG-05. `SCRIPT-SHORT` в обоих реальных прогонах

- **Где:** `script_length.py`, `checks.py`; сценарии `scenario.md` и `scenario (2).md`.
- **Факт:** 2 замечания в каждом сценарии: реплики педагога короче порога (например, 489 символов при пороге 600 для блока 10 мин).
- **Ожидаемо:** это `warning`, выдача разрешена с пометкой. Нужно решить, поднимать ли порог или считать замечание нормой для коротких блоков.
- **Влияние:** на приёмку не влияет, но снижает качество текста для учителя.

### BUG-06. Формат issue не соответствует ТЗ 16.2

- **Где:** QA-модуль (`code / severity / message / field`), сервис (`code / severity / location / message`).
- **Факт:** в ТЗ 16.2 есть `issue_id`, `category`, `repairable`, `suggested_action`.
- **Ожидаемо:** согласовать единый формат и маппинг; сейчас потребителю приходится знать два формата.
- **Влияние:** усложняет отображение и автоматическую обработку замечаний.

## P3

### BUG-07. Демо-каталог фронтенда расходится с реальным

- **Где:** `frontend/src/api.ts`, `DEMO_EVENTS`.
- **Факт:** в демо 2 события и `teacher_day`, в реальном каталоге 14 событий и `teachers_day`.
- **Ожидаемо:** демо-режим либо использует реальный каталог, либо явно помечен как учебный.
- **Влияние:** только демо-режим, на API-режим не влияет.

## Что проверено и работает

- `GET /api/v1/catalog/events` → 14 событий, `ural_culture` отсутствует.
- `POST /api/v1/generations` → 202, `knowledge_day` 45 мин: 5 блоков, сумма 45, старт с 0, `teacher_script` заполнен, `quality_report.status=passed`.
- Неизвестное событие → 422 `EVENT_NOT_FOUND`.
- Неподдерживаемый формат → 422 `CONFLICTING_CONSTRAINTS`.
- LLM-сервис остановлен → 503 `MODEL_UNAVAILABLE`, `retryable=true`, без переключения на mock.
- `partial` на Backend формируется корректно (1 из 3 вариантов), проблема только в отображении.
