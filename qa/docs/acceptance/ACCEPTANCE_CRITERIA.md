# Критерии приёмки сценария

Документ фиксирует, какой результат генерации считается готовым к выдаче педагогу. Опирается на ТЗ 16.1 и текущие проверки `qa/validators/`, `services/school_events_llm/qa/validators/` и интеграционный слой Backend. Пользовательские параметры — время, число детей, возраст, родители и ресурсы — являются входными ограничениями, а не экспертными вопросами.

## 1. Severity

| Severity | Смысл | Влияние на выдачу |
|---|---|---|
| `critical` | Сценарий структурно невалиден или противоречит входным данным | Выдача заблокирована |
| `high` | Серьёзный дефект качества, но сценарий технически можно показать | Выдача разрешена с обязательной пометкой «требует внимания» |
| `medium` | Заметное отклонение, которое желательно улучшить | Выдача разрешена, показывается предупреждение |
| `low` | Мелкое замечание или эвристика | Выдача разрешена, показывается как рекомендация |

`high` не блокирует выдачу в Sprint 2, но должен попадать в отчёт и по возможности исправляться через repair. `critical` не отдаётся педагогу никогда.

Внутренние уровни QA-модуля соотносятся с ТЗ 16.2–16.3 так:

| Внутренний severity | Severity в ТЗ | Статус проверки |
|---|---|---|
| `critical` | `critical` | `blocked` |
| `high` | `warning` | `warning` |
| `medium` | `warning` | `warning` |
| `low` | `info` | `passed`, если других проблем нет |

Сервис `services/school_events_llm` уже использует уровни ТЗ (`info / warning / critical`) и статусы (`passed / warning / blocked`). Четырёхуровневая шкала выше — внутренняя шкала QA-модуля, её нельзя выдавать за формат ТЗ без преобразования.

Формат issue в ТЗ 16.2 полнее, чем текущий ответ сервиса: `issue_id`, `category`, `severity`, `location`, `message`, `repairable`, `suggested_action`. QA-модуль отдаёт `code / severity / message / field`, сервис — `code / severity / location / message`. Расширение формата — отдельная задача, согласованная с Андреем.

## 2. Нормальный результат

Сценарий считается нормальным и готовым к выдаче, если:

- нет ни одного issue с `severity="critical"`;
- нет ни одного issue с `severity="high"`;
- `project.status="completed"`, а `completed_variants` равен запрошенному; `partial` допустим только с предупреждением и показом готовых вариантов;
- событие входит в единый каталог из 14 мероприятий; `ural_culture` и другие неизвестные ID отклоняются; карточка прошла `catalog-check` и содержит `values`, `regional_topics`, `facts_to_verify`, `age_appropriateness_notes`;
- в API-режиме нет тихого переключения на mock при недоступности LLM-сервиса;
- входные параметры валидны: `duration_minutes` из `30/45/60/90`, `pupils_count` от 1 до 35, `grade` входит в `grade_group`, правила `parents_count` соблюдены;
- нет потребности в ресурсе, который явно отмечен `false`; `null` считается неизвестным, а не доступным;
- фактические утверждения опираются только на `verified`-фрагменты; `draft`, `pending`, `needs_content_review`, `rejected` и другие не-`verified` статусы не выдаются за проверенный факт;
- число одновременно занятых учеников и групп не превышает `pupils_count`, педагогов — `teachers_count`, родителей в блоке — `parents_count`; роли и группы согласованы с реальными участниками;
- сумма `group_sizes` равна `pupils_count`;
- `concept.summary` и `concept.goal` заполнены;
- в `timeline` не меньше 2 блоков, у каждого есть непустой `teacher_script`;
- `teacher_instructions` содержит непустой список или строку;
- все `role_id`, `material_id` и `block_id` существуют;
- сумма `duration_minutes` равна запрошенной длительности;
- первый блок начинается с 0, между блоками нет разрывов и пересечений;
- при `parents_enabled=false` нет родительских ролей и включённого плана;
- при `parents_enabled=true` план включён, а число родителей в блоке не превышает `parents_count`;
- если материал требует печати, есть `printer` в `dependencies` или `resources.printer=true`.

`medium` и `low` могут присутствовать. Они не мешают выдаче, но отображаются педагогу как рекомендации.

## 3. Автоматические исправления и предупреждения сервиса

Сервис не только проверяет результат, но и исправляет формальные ошибки модели до проверки: `prepare_stage_output`, `reconcile_material_ids`, `complete_block_roles`. Каждое исправление пишется в трассу как `stage_output_fixed`. Если после исправления проверка всё равно падает, этап повторяется с текстом ошибки.

Предупреждения сервиса не блокируют выдачу, но должны быть видны в `quality_report`:

| Код | Смысл |
|---|---|
| `SCRIPT-SHORT` | Реплики педагога короче порога для длительности блока |
| `PUPIL-ACTIONS-FEW` | В блоке меньше двух действий учеников |
| `ROLE-UNUSED` | Роль есть в сценарии, но не задействована в блоках |
| `VOTING-NO-VOTERS` | Голосование объявлено, но нет голосующих |
| `PARENT-INSTRUCTION` | Нет памятки для родителей |
| `AWARD-INSTRUCTION` | Нет инструкции по награждению |
| `PREPARATION_CONFLICT` | Заведомо нереалистичное сочетание подготовки и формата |
| `FACT-SOURCE` | Утверждение не опирается на проверенный фрагмент; незарегистрированные даты — предупреждение |

Реальные прогоны от 26.10 содержат только `SCRIPT-SHORT`: по одному-два замечания на сценарий. По текущей модели это `warning`, выдача разрешена с пометкой.

## 4. Ошибки интеграции

Это не issue качества сценария, а ошибки уровня приложения. Они тоже влияют на выдачу.

| Ситуация | Код / статус | Поведение |
|---|---|---|
| LLM-сервис недоступен | `MODEL_UNAVAILABLE`, HTTP 503, `retryable=true` | Показать ошибку и повтор; не переключаться на mock |
| Неизвестное событие | `EVENT_NOT_FOUND`, HTTP 422 | Не запускать генерацию, показать ошибку каталога |
| Возраст или формат не поддержан событием | `CONFLICTING_CONSTRAINTS`, HTTP 422 | Показать ошибку параметров |
| Готовы не все варианты | `partial` | Показать готовые варианты и предупреждение; не выдавать за полный `completed` |
| Каталог или prompt-блок не согласованы | ошибка запуска сервиса | Не запускать генерацию до исправления каталога |
| `quality_report.status="blocked"` | `blocked` | Не показывать как готовый сценарий |
| Использован не-`verified` источник (`draft`, `pending`, `needs_content_review`, `rejected`) | критическая ошибка факта | Не выдавать утверждение как проверенное |

## 5. Что блокирует выдачу

Любой issue с `severity="critical"` блокирует выдачу. Коды в таблицах ниже — из QA-модуля `qa/validators/`; сервис использует свои коды, но те же уровни ТЗ. Для решения важнее severity и итоговый статус, чем конкретный код.

| Код | Что означает |
|---|---|
| `INVALID_VARIANT` | `variant` отсутствует или имеет неверный тип |
| `MISSING_COLLECTION` | Нет `timeline`, `roles` или `materials` либо это не список |
| `ORPHAN_ROLE_ID` | В блоке указана несуществующая роль |
| `ORPHAN_MATERIAL_ID` | В блоке указан несуществующий материал |
| `ORPHAN_BLOCK_ID` | Ссылка на несуществующий блок в ролях, материалах или плане родителей |
| `PARENT_ROLE_FORBIDDEN` | Есть родительская роль при `parents_enabled=false` |
| `PARENT_PLAN_FORBIDDEN` | План родителей включён при `parents_enabled=false` |
| `PARENTS_OVER_COUNT` | В блоке родителей больше, чем доступно по `parents_count` |
| `TIMING_INVALID_INPUT` | Нет тайминга или запрошенной длительности |
| `TIMING_INVALID_BLOCK` | Некорректные `start_minute` / `duration_minutes` |
| `TIMING_TOTAL_MISMATCH` | Сумма блоков не равна запрошенной длительности |
| `TIMING_START_NOT_ZERO` | Первый блок начинается не с 0 |
| `TIMING_NON_POSITIVE` | Длительность блока ≤ 0 |
| `TIMING_GAP` | Между блоками есть разрыв |
| `TIMING_OVERLAP` | Блоки пересекаются |

## 6. Что разрешает выдачу с пометкой

### High

Сценарий можно показать, но с предупреждением и записью в отчёте.

| Код | Что означает |
|---|---|
| `MISSING_FIELD` | Пустые `concept.summary`, `concept.goal`, `teacher_instructions` или `teacher_script` |
| `TOO_FEW_BLOCKS` | В `timeline` меньше 2 блоков |
| `PARENT_PLAN_MISSING` | Родители включены, но план отсутствует или выключен |
| `PRINTER_REQUIRED_MISSING` | Материал требует печати, но принтер не предусмотрен |

### Medium / low

| Код | Severity | Что означает |
|---|---|---|
| `AGE_LONG_BLOCK` | medium | Для `1-4` блок длиннее 15 минут |
| `AGE_LONG_WORDS` | low | Для `1-4` в `teacher_script` есть слова длиннее 12 букв |
| `AGE_ALL_SHORT` | low | Для `9-11` все блоки ≤ 5 минут |

## 7. Правило решения

```text
ошибка интеграции / нет проекта → не выдавать, показать ошибку и retry
critical > 0                     → не выдавать, repair / повторная генерация
critical = 0, high > 0           → выдать с пометкой «требует внимания»
critical = 0, high = 0           → выдать как нормальный результат
```

Пометка `high` должна быть видна педагогу и сохранена в `quality_report`. Если repair доступен, `high` лучше исправить до показа.

## 8. Что не входит в автоматическую приёмку

Экспертно проверяются смысловые, культурные, исторические и региональные вопросы, глубокая возрастная оценка и педагогическая реалистичность. Формальная реализуемость — время, ресурсы, число участников и групп — проверяется автоматически по ТЗ 16.1 A и не перекладывается на эксперта.

Роль эксперта в проекте выполняет учитель: на демо и в проде он видит предупреждения и решает, использовать ли сценарий. Отдельного методиста в команде нет, поэтому смысловая проверка не является блокером Sprint 2. Задача QA — довести до учителя всё, что можно проверить автоматически, и явно показать то, что автоматика не ловит.

Отдельно требуется кураторская проверка источников: автоматика видит статус фрагмента, но не заменяет сверку текста источника с утверждением. Сейчас в каталоге нет `verified`-фрагментов, поэтому исторические и региональные факты нельзя считать подтверждёнными.

Состав проверок описан в `qa/docs/acceptance/AUTO_VS_EXPERT.md`, вопросы для эксперта — в `qa/docs/acceptance/CONTENT_REVIEW_CHECKLIST.md`.
