# E2E-тест-кейсы приложения

Набор пользовательских сценариев для проверки единого приложения: фронтенд → основной Backend → LLM-сервис → модель. Основной режим — API-режим с реальной моделью, а не демонстрационный mock.

Перед прогоном:

```bash
# LLM-сервис с реальной моделью из .env
cd services/school_events_llm
python -m app serve

# Backend в другом окне
$env:GENERATOR_MODE="llm_service"
python -m uvicorn backend.main:app --port 8000
```

Один кейс на живой модели идёт 1,5–3 минуты, полный набор — 25–35 минут. Если модель недоступна, допускается `LLM_SERVICE_FIXTURE_MODE=true`, но это проверка интеграции, а не качества генерации.

Каталог проверяется через `GET /api/v1/catalog/events`: должно быть 14 событий, без `ural_culture`.

Ограничение интерфейса: форма не позволяет выбрать роли родителей и режим участия (`helper`, `evaluator`, голосование), поэтому кейсы 04, 06, 12 через UI воспроизводятся только частично — их гоняем по API (BUG-08).

## Негативные проверки

| Проверка | Запрос | Ожидаем |
|---|---|---|
| Неизвестное событие | `event_id=ural_culture` | 422 `EVENT_NOT_FOUND` |
| Неподдерживаемый формат | `last_bell` + `interactive_lesson` | 422 `CONFLICTING_CONSTRAINTS` |
| Сервис недоступен | LLM-сервис остановлен | 503 `MODEL_UNAVAILABLE`, `retryable=true`, без mock |
| Не все варианты готовы | `variants_count=3` | `partial`, готовые варианты доступны |

## Как использовать

1. Запустить LLM-сервис и Backend в API-режиме (`GENERATOR_MODE=llm_service`).
2. Проверить каталог и источники: `catalog-check`, `sources-check`.
3. Прогнать каждый кейс через пользовательский путь: выбор события → параметры → генерация → проект.
4. Проверить HTTP-коды, `job.status`, `project.status`, `completed_variants`.
5. Проверить `quality_report`: отсутствие `critical`, наличие ожидаемых предупреждений.
6. Проверить автоматические ограничения: сумму времени, ресурсы, число учащихся/педагогов/родителей, сумму групп.
7. Для содержательных вопросов пройти `qa/docs/acceptance/CONTENT_REVIEW_CHECKLIST.md`.
8. Отдельно проверить долгое ожидание: индикатор прогресса, отсутствие «зависшего» экрана и понятное сообщение при `partial` и `failed`.
