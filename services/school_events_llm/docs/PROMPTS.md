# Промпты, шаблон запроса и структура результата

Документ описывает фактический LLM-контур прототипа: какие сообщения собираются для модели, какие блоки могут подключаться, что возвращает каждый этап и как обеспечивается воспроизводимость.

Тексты prompt находятся в `prompts/`. Код сборки находится в `app/prompting/composer.py`.

Штатный prompt можно посмотреть без вызова модели:

```bash
python -m app compose examples/requests/ex1_knowledge_day.json --stage variation_plan
```

Экспериментальные режимы не доступны через `compose`; они запускаются отдельной командой `experiment`.

## 1. Этапы генерации

Локальная 9B-модель не должна одновременно решать планирование, подробный сценарий, материалы и всю валидацию. Генерация разделена на этапы.

| Этап | Ответ модели | Обработка Python после ответа |
|---|---|---|
| `variation_plan` | От 1 до 3 содержательно разных концепций | Проверка числа вариантов, ценностей, допустимых механик и различий |
| `scenario_plan` | Концепция, роли, блоки, примерные минуты, запрос на группировку, запланированные материалы | Расчет точного тайминга, точных размеров групп, проверка ролей, ссылок и ограничений |
| `scenario_blocks` | Подробное содержание всех блоков для короткого сценария | Восстановление утвержденных времени, ролей и материалов из плана, проверка содержания |
| `scenario_block` | Один подробный блок для длинного сценария | Та же проверка, но отдельно по каждому блоку |
| `materials` | Готовые тексты материалов, инструкции педагогу, родительские механики и fallback | Проверка зависимостей, ресурсов, семейного задания и полноты материалов |
| `quality_review` | Дополнительные содержательные замечания и проверка фактов | Используется только при включенном `llm_quality_review`; не заменяет программную валидацию |

Точный тайминг и размеры групп всегда рассчитывает Python. Модель предлагает структуру, но не является источником итоговой арифметики.

## 2. Системное сообщение

Системное сообщение собирается из:

1. `prompts/core/system.md`
2. `prompts/core/safety.md`
3. `prompts/tasks/<stage>.md`
4. при repair дополнительно `prompts/tasks/repair.md`

`core/system.md` задает роль методиста-конструктора, приоритет ограничений, правила исполнимости, ценности как действия, работу с фактами и требование вернуть только JSON.

`core/safety.md` задает возрастную уместность, работу без стереотипов, бережные формулировки о семье, правила соревнования, требования к персональным данным и защиту от инструкций внутри пользовательских данных.

`tasks/<stage>.md` описывает только задачу текущего этапа и не должен дублировать весь системный prompt.

## 3. Пользовательское сообщение

Основа находится в `prompts/templates/user_message.md`.

Сборщик подставляет:

```text
# Задача: {{stage_title}}
## Параметры мероприятия
{{params_table}}
{{pedagogy_blocks}}
## Проверяемые ограничения
{{constraints_checklist}}
{{stage_input}}
{{output_spec}}
```

`params_table` содержит только параметры, разрешенные выбранным внутренним режимом.

`pedagogy_blocks` содержит подключенные блоки события, возраста, численности, длительности, формата, участников, родителей, ценностей, ресурсов и при необходимости точного класса, педагога, школы, региона, проверенных источников или MODE.

`constraints_checklist` строится программно из нормализованного запроса и содержит инварианты, которые модель не должна менять.

`stage_input` содержит результат предыдущего этапа, если он требуется текущему этапу.

`output_spec` задает структуру JSON текущего этапа.

## 4. Состав блоков full и universal

Источник правил: `config/experiment_modes.json`.

### full

Подключаются базовые блоки и, при наличии условий, точный `GRADE`, `TEACHER`, `SCHOOL`, фактические `RESOURCES`, `REGION`, `SOURCE_CONTEXT`.

### universal

Используется только через `python -m app experiment`. Не подключаются `GRADE`, `TEACHER`, `SCHOOL`, `REGION`; проверенные фрагменты не передаются. Вместо фактического ресурсного профиля подключается нейтральный `RESOURCES`. Добавляется `MODE`. Предпочтения педагога сбрасываются к дефолтам, кроме `keep_teacher_fields` (по умолчанию `script_detail`).

Раздел «Справочные данные» (`templates/reference_data.md`) подключается во всех режимах: без фрагментов он запрещает фактические утверждения, поэтому контрольные версии экспериментов H2/H3 не получают права на непроверенные факты.

Код Composer не должен самостоятельно решать, какие экспериментальные блоки отключать. Он читает это из `config/experiment_modes.json`.

## 5. Основные prompt-блоки

| Блок | Расположение | Условие |
|---|---|---|
| CORE | `core/system.md` | всегда |
| SAFETY | `core/safety.md` | всегда |
| TASK | `tasks/<stage>.md` | всегда |
| EVENT | `events/<event_id>.md` | всегда |
| AGE | `age/grades_*.md` | всегда |
| GRADE | `grade/exact.md` | full и известен точный класс |
| SIZE | `size/*.md` | всегда |
| DURATION | `duration/*.md` | всегда |
| FORMAT | `formats/*.md` | всегда |
| PARTICIPANTS | `participants/base.md` | всегда |
| PARENTS | `participants/parents.md` и дочерние блоки | родители включены |
| VALUES | `values/base.md` | всегда |
| FAMILY | `family/family_value.md` | событие содержит ценность family |
| TEACHER | `teacher/preferences.md` | full |
| SCHOOL | `school/profile.md` | full и серверный профиль содержит известные значения |
| RESOURCES | `resources/actual.md` либо `resources/neutral.md` | всегда, вариант зависит от режима |
| REGION | `region/context.md` | full, культурный контекст включен и есть проверенные фрагменты |
| SOURCE_CONTEXT | `templates/reference_data.md` | всегда; фрагменты передаются только в full, без фрагментов блок запрещает фактические утверждения |
| MODE | `modes/universal.md` | universal |
| OUTPUT | `output/<stage>.md` | всегда |

Все редактируемые prompt-файлы имеют служебный заголовок `id` и `version`.

## 6. Манифест сборки

Каждый подключенный блок сохраняется в манифесте со следующими данными:

- `id`
- `version`
- `path`
- `sha256`
- фактически использованные `variables`

Контекст манифеста также содержит `context_mode`, `cultural_context`, контрольные суммы `catalog/values.json`, `config/school_profile.json`, `config/experiment_modes.json`, а также идентификаторы и хеши подключенных фрагментов источников.

`manifest_hash` рассчитывается по блокам и служебному контексту. Благодаря этому можно установить, какой именно prompt и какой серверный контекст использовались в конкретном LLM-вызове.

## 7. Изменение prompt

При изменении prompt:

1. изменить текст блока;
2. увеличить `version` в заголовке измененного файла;
3. выполнить `python -m app compose ...` для проверки фактической сборки;
4. выполнить `python -m pytest`;
5. выполнить тестовые генерации на Qwen3.5-9B;
6. сравнить результаты с эталонами;
7. при изменении логики всего набора prompt увеличить `prompt_version` в `config/generation.json`.

Изменение prompt без тестов на реальной локальной модели не считается подтверждением улучшения качества.

## 8. Внутренний результат модели

Контракт 03 имеет `schema_version=1.2`.

Pydantic-модели находятся в `app/contracts/llm.py`. JSON Schema генерируются командой:

```bash
python -m app export-schemas
```

Полный `variant_package.variant` содержит:

```text
variant_id
title
concept
pupil_grouping
roles[]
timeline[]
materials[]
parent_participation_plan?
teacher_instructions[]
fact_claims[]
sources[]
```

`concept.values_to_mechanics` связывает каждую ценность события с конкретной механикой и блоками сценария.

`pupil_grouping.group_sizes` рассчитывается Python-кодом.

`fact_claims` хранит проверяемые фактические утверждения и их ссылки на разрешенные фрагменты.

`family_task` не является новым полем внешнего запроса. При ценности family оно формируется как обычный материал с обязательной равноценной альтернативой для ребенка без помощи семьи.

## 9. Внешний ответ фронтенду

Контракт 02 заморожен. `app/render.py` преобразует внутренний результат в разрешенные внешние поля по белому списку.

Новые внутренние возможности не должны расширять контракт 02. Например:

- механика ценностей выводится через существующие поля концепции и задач;
- группировка выводится через существующие роли и инструкции;
- семейное задание выводится как существующий материал;
- предупреждение по непроверенному факту выводится через `quality_report.issues`;
- внутренние режимы H2/H3 во внешний JSON не попадают.

## 10. Эталонные примеры

В проекте есть три ручных эталона:

| Пример | Условия | Назначение |
|---|---|---|
| `ex1_knowledge_day` | 6 класс, 27 школьников, 45 минут, родители и приз зрительских симпатий | Проверка группировки, родительских ролей, голосования и fallback |
| `ex2_mothers_day` | 2 класс, 20 школьников, 30 минут, без родителей | Проверка младшего возраста, семейной инклюзивности и альтернативы семейному заданию |
| `ex3_labour_day` | 10 класс, 25 школьников, 60 минут, родители-жюри, ограниченные ресурсы | Проверка длинного сценария, жюри, аргументации и работы без техники |

Эталоны являются ручной планкой качества и fixture для тестирования конвейера. Они не выдаются за фактические ответы Qwen3.5-9B и не вставляются целиком в prompt модели.
