# Интеграция Backend Severus и school_events_llm

## Цель

Подключить независимый LLM-модуль к существующему FastAPI Backend без изменения внешнего JSON-контракта Frontend.

## Принятое решение

Frontend продолжает обращаться только к основному Backend на `/api/v1/...`.

Backend поддерживает два режима:

- `GENERATOR_MODE=mock` - текущий локальный mock;
- `GENERATOR_MODE=llm_service` - внутренний HTTP-вызов `school_events_llm`.

LLM-сервис по умолчанию запускается на `127.0.0.1:8090`. Браузер к нему не обращается, CORS ему не требуется.

Поток данных:

```text
Frontend
  -> Backend :8000
  -> school_events_llm :8090
  -> выбранная LLM или fixture
  -> school_events_llm
  -> Backend
  -> Frontend
```

Контракт между Frontend и Backend и контракт между Backend и LLM-сервисом имеют одинаковое тело запроса. Backend не переводит поля и не хранит отдельную LLM-схему.

## Каталог мероприятий

В актуальном `main` общий каталог содержит 14 событий. Предыдущая версия LLM-модуля содержала 13 событий, потому что объединяла два региональных направления в `ural_culture`.

Теперь LLM-модуль использует те же ID, что и общий каталог:

- `sverdlovsk_oblast_day`;
- `middle_urals_peoples_day`.

`ural_culture` удалён из активного набора.

В монорепозитории общий `catalog/events/` является единственным источником истины для карточек событий, включая ID, названия, возрастные группы, форматы, образовательные цели, `values`, `regional_topics` и версию каталога. LLM-сервис не хранит копию карточек событий; специфические для генерации инструкции находятся только в `services/school_events_llm/prompts/events/<event_id>.md`. При загрузке сервис проверяет наличие prompt-блока для каждого события.

## Настройки Backend

Переменные окружения:

```dotenv
GENERATOR_MODE=llm_service
LLM_SERVICE_URL=http://127.0.0.1:8090
LLM_SERVICE_TOKEN=
LLM_SERVICE_HTTP_TIMEOUT=10
```

Для возврата к текущему mock:

```dotenv
GENERATOR_MODE=mock
```

Тихого fallback с `llm_service` на `mock` нет. Если LLM-сервис недоступен, Backend возвращает `503 MODEL_UNAVAILABLE` с `retryable=true`.

## Настройки LLM-сервиса

Для обычной модели:

```dotenv
ACTIVE_MODEL=qwen_local_9b
SERVICE_HOST=127.0.0.1
SERVICE_PORT=8090
SERVICE_AUTH_TOKEN=
```

Для тестового запуска без модели:

```dotenv
LLM_SERVICE_FIXTURE_MODE=true
```

Запуск:

```bash
cd services/school_events_llm
python -m app serve
```

## Реальные модели

Локальная Qwen через LM Studio остаётся доступна как `qwen_local_9b`.

Для OpenAI-compatible шлюза команды адрес и ключ задаются только через окружение:

```dotenv
LITELLM_BASE_URL=
LITELLM_API_KEY=
```

Адрес шлюза и полный виртуальный ключ хранятся только в локальном `.env` или секретах хостинга. В `config/models.json` остаются только имена ENV-переменных. Административные поля Team/Key ID для API-вызова не требуются и намеренно не сохраняются в коде.

Штатно доступны профили `urfu_qwen_27b`, `urfu_gigachat_3_pro`, `urfu_gigachat_2_max` и `urfu_gigachat_2_pro`. Экспериментальные `abliterated/uncensored` профили описаны, но оставлены выключенными.

После добавления рабочего ключа доступ проверяется командами:

```bash
python -m app health --model urfu_qwen_27b
python -m app health --model urfu_gigachat_3_pro
```

## Что проверено автоматически

Интеграционный тест проверяет полный сценарий:

1. POST запроса в основной Backend.
2. Передача того же JSON во внутренний LLM HTTP API.
3. Нормализация и запуск реального конвейера LLM-модуля.
4. Использование подготовленного fixture-ответа вместо реальной модели.
5. Формирование контракта 02.
6. Получение результата через публичный endpoint Backend.
7. Проверка точной длительности сценария и совпадения `job_id` / `project_id`.

Отдельно проверяется совпадение эффективного входного JSON Backend и LLM-модуля и точное совпадение всех 14 `event_id`.

## Что ещё требуется для продуктивного режима

- добавить полный рабочий `LITELLM_API_KEY` только в локальное/серверное окружение;
- провести smoke-тест доступных моделей через подтверждённый шлюз;
- выбрать основную модель по качеству и времени ответа;
- заменить временное in-memory хранение задач на постоянное;
- отдельно согласовать политику таймаутов и повторных попыток;
- завершить кураторскую проверку источников для фактических и региональных утверждений.

## Результат проверки интеграционной сборки

Финальная интеграционная проверка должна выполняться после каждого изменения каталога или LLM-сервиса:

```bash
python catalog/tools/build_catalog_index.py --check
python -m pytest -q
cd services/school_events_llm
python -m app catalog-check
python -m app sources-check
python -m pytest -q
```

Также рекомендуется отдельный smoke-тест реального HTTP-вызова `Backend -> LLM-service -> Backend` в fixture-режиме. Реальный внешний LLM-шлюз проверяется только при наличии полного рабочего ключа в локальном/серверном окружении; ключи и адрес шлюза в репозиторий не записываются.

Техническая синхронизация каталога выполнена. Содержательное наполнение региональных карточек и кураторский корпус проверенных фактов остаются предметом согласования с ответственным за каталог.
